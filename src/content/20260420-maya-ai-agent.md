## はじめに

この記事は、普段Mayaでモデリングやアニメーションをしているけれど、Pythonやスクリプトには苦手意識がある方に向けて書いています。
「AIエージェントって、結局エンジニア向けのツールなんでしょ？」と思っている方に、「いや、むしろ書けない人ほど恩恵が大きいかもしれません」という話をしたいです。

この記事では「どこから始めればいいか」に絞って話します。GitHub Copilot のインストール手順のような導入方法や、各AIサービスの機能比較は扱いません。

## 結論（TL;DR）

- 最近のAIエージェントは、**コードを書く人の補助**というより、**仕事を進める人の補助**に近づいてきています。
- Mayaのモデラーやアニメーターのように、普段コードを書かない方でも「どうなっていれば成功か」を日本語で説明できれば、AIがかなりの部分を肩代わりしてくれます。
- ただし、環境セットアップや社内固有の作法はAIが苦手な領域です。ここだけは、ツール担当のエンジニアに協力してもらうのが現実的です。
- 最初の一歩としては、毎回やっている**地味なチェック作業**を一つだけ任せてみるのがおすすめです。
- Maya 本体も AI 機能を持ち始めており、今の時点で外部ツールを試しておく価値は十分あります。

## 前提知識の確認

ここでいう「AIエージェント」は、GitHub Copilotのようなコーディング支援ツールの延長にある、**自律的に作業を進めてくれるタイプ**のAIを指しています。
単にコード補完をしてくれるだけでなく、指示を受けて自分で試行錯誤し、結果を確認して、必要なら修正までしてくれる、というイメージです。

GitHub Copilot は、Microsoft と GitHub が提供している AI コーディングアシスタントです。エディタやチャット上から使えます。Claude は Anthropic が提供する AI アシスタントで、文章作成や調査など幅広い用途に使えます。ご存じの方は読み飛ばしてください。

## 少し前までの印象と、いま起きている変化

少し前までは、AIエージェントにできることといえば、コードの補完や、ちょっとしたサンプル生成、といった印象が強かったと思います。
「使えるのはエンジニアだけ」「自分には関係ない」と感じていた方も多いのではないでしょうか。

最近はそうでもなくなってきています。
目的や成功条件がはっきりしている作業については、人が細かく手を動かさなくても、AIがかなりの部分を進めてくれる場面が増えてきました。

ここがポイントで、重要なのは「AIにコードを書かせること」そのものではなく、**「どうなっていれば成功か」を自然言語で伝えられること**です。
つまり、これまで自動化のためにはPythonを書ける必要があった場面でも、今は必ずしもそこから始めなくてよくなっています。

## モデラー・アニメーターにとって何が嬉しいのか

たとえば、普段のMayaでの作業を思い出してみてください。

- マテリアルが正しくアサインされているか確認する
- シェイプのアトリビュートが想定通りの値になっているか見る
- ノードのつながり方に不整合がないかチェックする
- 命名規則に従っているかを一通り確認する
- 書き出し前にヒストリが残っていないかを確かめる

こういった作業は、**一つひとつは難しくないけれど、確認箇所が多くて、地道で、人がやると見落としが出やすい**タイプの仕事です。
正直、つらいですよね。

このタイプの作業は、AIととても相性が良いです。
「このケースではこのマテリアルが付いていてほしい」「この属性はこの値になっていてほしい」「このノードはヒストリが消えていてほしい」——こうした**成功条件を言葉にできれば**、AIはそこに向かって、自分でシーンを確認したり、ログを読んだり、必要なら簡単なスクリプトを書いて実行したりしながら、作業を進めてくれます。

コードを書けなくても大丈夫です。
むしろ、「作業のゴールが何か」を一番よく知っているのは、日々そのシーンを触っている本人です。
その知識を言葉にできるかどうかのほうが、Pythonの文法を覚えているかどうかよりも、ずっと大事になってきています。

## よくある勘違い

よくある勘違いとして、「環境セットアップも含めてAIに全部任せられる」と思ってしまうことがあります。ここで少し先回りして整理しておきます。

結論から言うと、**環境セットアップは今でもAIが比較的苦手な領域**です。

理由は単純で、環境セットアップには会社独自の方法や、チームの暗黙知、古くからの運用ルールが入り込みやすいからです。
たとえば、どの順番でツールを入れるのか、どの設定ファイルをどこに置くのか、権限やパスの扱いをどうするのか、といった情報は、外から見ただけでは分かりません。しかも、そういう情報ほど文書化されていなかったりします。

たとえば、Windows環境で `mayapy` を使って検証用スクリプトを動かす作業をAIに手伝ってもらいたいとします。
`mayapy` は、Maya に付属している Python 実行環境です。GUI の Maya を開かずに、Maya 系の Python スクリプトを実行したいときによく使います。
このときAIに必要なのは、「Pythonを実行する」という一般論ではなく、**「この会社ではどの `mayapy` をどう使うのが正しいのか」**という具体的な手順です。
実際の現場では、単に `mayapy.exe` を叩けば終わり、ということはあまりありません。バージョン指定や環境変数、プラグインパス、作業ディレクトリの前提が付いてくることが多いです。めんどくさいですよね。
こういう実行方法は一般には分からないので、まずはそれを管理しているエンジニアから「正式な実行手順」を教えてもらう必要があります。

ここはモデラー・アニメーターが単独で抱え込む部分ではありません。
ツール担当のエンジニアに**「AIに作業を任せたいので、環境の前提を文章にしてもらえませんか」**と相談するのが、一番の近道です。

## 前提知識を残しておく場所

入手した環境の前提知識やルールは、AIが参照しやすい形で残しておくと扱いやすくなります。
GitHub Copilot を使う場合、置き場所は大きく2つあります。

- **インストラクション**（`.github/copilot-instructions.md` など）: 常に参照してほしいルール・前提
- **スキル**（`.github/skills/<name>/SKILL.md`）: 特定の作業をするときだけ参照してほしい手順

配置のイメージはこんな感じです。

```text
.github/
├─ copilot-instructions.md        # 常時参照するルール（命名規則など）
└─ skills/
   └─ windows-mayapy/
      └─ SKILL.md                  # 作業時に参照する手順（mayapy の実行）
```

ざっくり言うと、「いつも守ってほしいこと」と「特定の作業のときだけ必要な手順」を分けておく、というイメージです。

### 例1: スキルで「mayapy の実行方法」を渡す

たとえば、mayapy を動かすときの社内固有の手順は、作業時だけ必要な知識なので、スキルにするのが向いています。

`.github/skills/windows-mayapy/SKILL.md` の中身は、たとえば次のような形になります。

```md
---
name: windows-mayapy
description: Windows 環境で社内標準の手順に従って mayapy を使うときに参照するスキル。
---

# Windowsでmayapyを使うときの前提

社内のパイプラインツール上で構築された mayapy を使う方法。

## 目的

- Windows 環境で、社内標準の設定を読み込んだ状態で mayapy を実行する。
- Maya 向けの検証スクリプトや補助スクリプトを、想定したバージョンで動かす。

## 正式な実行方法

- 使用バージョン: Maya 2025
- 実行コマンド: `D:\studio_tools\launchers\start_mayapy_2025.bat`
- 作業前提: プロジェクトの作業ディレクトリで実行する

## 注意点

- `mayapy.exe` を直接実行しない
- 社内バッチを通さないと、必要な環境変数やプラグインパスが不足することがある
- 実行に失敗した場合は、まず起動バッチの更新有無をツール担当者に確認する

## 成功条件

- スクリプト内で必要な Maya API が import できる
- 対象プロジェクト向けの設定が読み込まれた状態で処理を実行できる

```

こうしておけば、「この mayapy スキルを使って、このスクリプトを実行してみて」と指示するだけで、AI が社内の作法に沿って動いてくれるようになります。

### 例2: インストラクションで「命名規則」を渡す

一方で、命名規則のように**どの作業でも守ってほしいルール**は、スキルではなくインストラクションに書いておくのが向いています。
インストラクションはリポジトリの中で常に読み込まれるので、わざわざ「このファイルを見て」と指定しなくてもAIが前提として扱ってくれます。

`.github/copilot-instructions.md` に、こんな感じで書いておきます。

```md
# このリポジトリの命名規則

## ジオメトリ（トランスフォーム）
- 末尾に `_geo` を付ける。例: `character_body_geo`

## グループノード
- 末尾に `_grp` を付ける。例: `character_root_grp`

## ジョイント
- 末尾に `_jnt` を付ける。例: `spine_01_jnt`

## ロケーター
- 末尾に `_loc` を付ける。例: `pivot_ref_loc`

## 共通ルール
- すべて小文字＋スネークケース
- 空白・日本語・記号（`-` を除く）は使用しない
```

こうしておけば、たとえばAIに

> 「このシーンファイル（.ma）を読んで、命名規則に違反しているノードを一覧にしてください」

とお願いするだけで、保存済みの .ma ファイルをテキストとして解析し、違反箇所をリストアップしてくれます。
Maya を開いたまま操作するのは現状難しいですが、保存済みのファイルを対象にした確認作業なら十分こなせます。書き出し前の最終チェックに向いています。
毎回ルールを貼り付けなくていい、というのがインストラクションの強みです。

### 使い分けのコツ

雑にまとめると、こんな感覚です。

- **常に守ってほしいルール** → インストラクション（例: 命名規則、コーディング規約、用語集）
- **特定の作業のときだけ参照する手順** → スキル（例: mayapy の実行手順、書き出し手順、リグチェックの流れ）

この整備は一度やってしまえば、以降はモデラー・アニメーター側から「この条件で〜を確認して」と指示するだけで、AIがその前提の上で動いてくれるようになります。

## 人間の役割はどう変わるか

AIは、繰り返しの確認や、条件が明確なチェック、ログを見ながらの切り分けのような作業には強いです。
一方で、社内固有の文化、文書化されていない前提、曖昧な判断が必要な場面では、まだ人が支える必要があります。

なので、「全部AIに任せる」ではなく、**「何をAIに任せると効果が出るのか」を見極める**ことが大事です。
人間の役割も、すべてを自分で実装することから、成功条件を定義して、任せ方を設計して、最後に結果を判断することへ、少しずつ移ってきているのだと思います。

モデラー・アニメーターの皆さんは、「コードを書けないからAIは関係ない」と感じやすい立場かもしれませんが、実は逆です。
**成功条件を一番具体的に語れるのは現場の人**なので、AIと一番噛み合うポジションにいます。

## 将来はMayaだけで十分になるかもしれない

今後、Maya のアップデート次第では、わざわざ Copilot や Claude のようなツールを学ぶ必要がなくなる可能性もあると思います。
実際、Maya 2027 ではすでに AI 機能の導入が始まっており、チャットで質問すると回答を返してくれる機能が実装されています。

ただ、それでも外部ツールを試しておく価値がある理由がいくつかあります。

まず、プロダクションでは常に最新バージョンをそのまま使えるとは限りません。バージョン固定や運用ルールの都合で、Maya 2027 の機能が手元で使えるまでに時間がかかるケースは珍しくありません。

次に、Maya 内の AI はあくまで Maya の中の作業に特化しています。パイプライン全体を見ると、書き出し後のファイル整理、他部署への連絡、Houdini や Nuke といった別のDCCツールとの橋渡し、社内向けドキュメントの作成など、Maya の外で発生する作業も多くあります。こういった部分には、外部の AI エージェントのほうが向いています。

つまり、Maya 本体の AI と外部ツールは競合するものではなく、得意領域が違う補完関係にあります。

それに、Copilot や Claude のようなツールは、Maya の作業以外にも、ちょっとした調べものや文章の整理、こういう記事の執筆のような作業にも使えます。

なので、将来的に Maya 本体がどんどん賢くなっていくとしても、今の時点で一度試してみるのは悪くない、と個人的には感じています。

## まとめ

- AIエージェントは「コードを書く人の補助」から「仕事を進める人の補助」へ近づいています。
- コードが書けなくても、「どうなっていれば成功か」を自然言語で説明できれば、AIに任せられる作業は多いです。
- まずは、日常的にやっている地味なチェック作業を一つだけ任せてみるところから始めるのがおすすめです。
- 環境セットアップや社内固有の作法はAIが苦手なので、ツール担当エンジニアに協力してもらい、`.github` 配下などに前提知識を残しておきましょう。
- 「常に守ってほしいルール」はインストラクションに、「特定の作業のときだけ参照する手順」はスキルに、と置き場所を分けておくと扱いやすくなります。
- Maya 本体も AI 化が進んでいますが、プロダクションのバージョン制約や Maya 外の業務（文章整理・調査など）を考えると、外部ツールを今試しておくのは損ではありません。
- AIは万能ではありませんが、うまく使えば頼れる相棒になってくれます。

小さいところから、気軽に試してみてください。
